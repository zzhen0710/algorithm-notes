## 整理顺序与扩展标记

先整理第十八届蓝桥杯大纲中 B 组及其包含的 C 组内容；同一主题内先基础后组合应用，主题之间可交叉推进。大纲中的基础排序与容器通过已有笔记和 STL 使用说明复用，不要求重复手写。

B/C 组内容全部完成整理后，再按实际需要补充 A 组专项。数位 DP、Manacher、LCA、差分约束、连通性、二分图匹配、高斯消元等属于 B 组范围，仍需保留，不因难度较高而移入 A 组。

A 组新增条目的标题和索引前统一显示字面星号 `*`，正文注明“扩展内容”；Markdown 中可写作 `\* AC 自动机`。星号表示 A 组扩展范围，不表示难度；B/C 组条目不使用这一标记。扩展内容归入现有主题，不单独建立 A 组目录。

## 与 ds-notes 的分工

| 内容 | 本仓库的处理 |
| --- | --- |
| 基础排序与基础容器 | 复用已有原理；普通排序使用 `sort`，稳定排序使用 `stable_sort`，容器优先使用 STL |
| KMP、并查集、最短路、最小生成树、拓扑排序等 | 保留支撑实现的必要原理，整理简洁、带注释的竞赛模板与应用边界 |
| 树状数组、线段树、ST 表等 | 正式纳入知识目录，解释操作、维护信息、复杂度与实现 |
| 归并计数、单调结构等应用 | 独立整理算法方法，不能以已有排序或容器知识代替 |

避免复制完整教材推导，但不省略理解和正确实现所需的定义、不变量与证明。已有笔记不自动代表所有竞赛变形已经掌握。

## 笔记与模板规范

知识正文包含：解决的问题与适用条件、核心状态或不变量、必要推导、带注释的关键实现、复杂度、易错边界，以及“典题与复盘”板块。索引和总览不单独配题；紧密相关的 STL API 条目可共用专题典题，但应有明确链接。

完整可复用代码放在 [Templates](../templates/README.md)，笔记保留解释所需的片段并链接模板；每个算法优先维护一种主写法。DP、贪心按具体模型整理，不强行设计万能模板。

典题代码默认展示完整 `solve()` 与必要辅助函数；通用头文件、类型别名和 `main` 若无改动，引用[竞赛基础模板](../templates/cpp-contest-template/README.md)，不重复展开。涉及框架改动时再展示相关部分。

模型导引单独列出变量的含义与作用、容器按什么规模分配、下标范围与题目值域；再用独立小节分点说明输入、预处理、执行流程、状态更新和输出。记录数决定的数组范围与按值比较的阈值必须区分。

每章末尾维护总结与选型：比较可互相替代的方法、代码长度、现场重写和理解记忆成本；优先用已出现典题多解，不为总结强行增加新题。原 AC 与既有复盘留在原节，新增的横向对比解法可在总结维护，原节标注“其他解”并双向链接。未完成章节可先整理标明覆盖范围的阶段版，不能据此标全章完成。

## 典题与复盘

新增或实质修订知识笔记时，按以下流程组织典题；已有“代表题”板块可逐节沿用并补齐，不批量伪造个人做题记录。

### 做题前：给题与独立尝试

- 配套典题只选洛谷或 Codeforces，不选其他平台。
- 提供 1 道或多道可点击的题目链接，按覆盖不同知识点与变形选择，不凑题量；通常先给 1–3 道，确有需要再增加。
- 核对原题的题号、标题、约束和知识前置。无法访问原题时明确未核验，不猜题意、难度或约束。
- 先给链接、简短练习目的与建议顺序，状态标为“待做”；不提前写入该题完整解答或核心突破。学习算法所需的通用模板仍可正常讲解。
- 本人独立尝试并提供代码、思路及已有评测结果后再核验；需要帮助时可按请求逐步提示。

### 做题后：核验与双解复盘

典题正文依次记录：

1. **题目与约束**：原题链接、简短题意、影响选型的数据范围与条件。
2. **原 AC／我的做法**：据本人实际提交的思路和代码整理，保留关键推理、实现与复杂度。原 AC 保留原有逻辑，格式或注释整理应注明；有学习价值的错误片段另行标错，修正版不能冒充原实现。
3. **核验结果**：分别记录平台评测结果、本地样例/边界/对拍结果和静态分析；仅样例通过不写成 AC。发现错误时给出具体反例或失败原因，记录修正后再验证的结果。
4. **完善 AC／推荐做法**：保留必要推导、正确性依据、带注释的实现、复杂度与适用边界。这里的“完美 AC”指经过充分推敲的完善版本，不宣称唯一最优，也不把更短代码视为更优。
5. **进步空间**：具体比较时间、空间、实现复杂度与易错点，指出收益和代价；从原方案的重复计算、冗余状态或遗漏性质解释为何改进有效。
6. **如何想到**：写清“题目线索 → 原做法瓶颈 → 可利用性质 → 转化/算法选择”的推理链，并说明何时不适用。
7. **迁移与重做**：提炼一两条可复用判断；值得独立成篇时链接对应范式或模板。

两种实现有实际差异时，在本题下并列保留原 AC 与完善 AC 的代码和分析；原做法已经合适时，完善版本可引用同一实现，只补论证、边界或权衡，不凑第二份代码。AC 标记应有相应平台通过依据，评测结果需注明依据；只有静态分析或本地测试的代码标为“原实现／改进实现”，待确认后再标 AC。错误原稿只保留有学习价值的片段并明确标错，不暗中覆盖。

正文统一采用个人笔记口吻：思考过程可用“我的思路／原做法”，技术分析优先用“原实现／改进实现”等客观表述；不使用面向读者的第二人称称呼，也不写协作会话或代码交接过程。原实现与改进实现仍需区分，平台 AC、本地核验和掌握状态如实记录。

### 状态与正文位置

典题状态按实际记录为“待做 → 已提交待核验 → 已核验待复盘 → 复盘完成”；发现问题时转为“待修正”，修正后重新核验。缺少本人代码或验证依据时保留待办，不代写“我的做法”，不推断已经掌握。

为学习某项知识而安排的配套典题，原 AC、完善 AC 与改进分析完整写在所属笔记，参考现有枚举、模拟章节的组织方式。题解较长或涉及多个专题也不迁入 Problems；其他章节需要时链接原位置。

[Problems](../problems/README.md) 用于独立刷题、比赛或补题中发现并专门积累的好题。归档看收录来源与目的，不看题解长度或是否跨专题；笔记典题不再以题目条目重复加入 Problems 索引。若独立好题用于说明某项知识，笔记可作简短引用并链接其已有正文。

跨题可复用的识别与建模方法提炼到 [Patterns](../patterns/README.md)，稳定实现进入 [Templates](../templates/README.md)。提炼时先检索已有条目，优先补充与互链，不为每题新建一种范式。
